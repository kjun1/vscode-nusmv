# NuSMV モデルを書くときに使える機能

LiCRuM 版 0.12.0 は、モデルと検査式を別々のファイルに書いても、定義を確かめながら編集できることを重視しています。たとえば `CTLSPEC EF front.is_open` と書いたとき、「`is_open` は何を表すのか」はエディタで確認できます。「実際にドアが開く経路があるか」は NuSMV を実行して調べます。

## 今使える機能

| やりたいこと | エディタでできること |
| --- | --- |
| モデルを書く | キーワードや変数、列挙値を色分けします。入力中の式では使える名前を、`front.` の後ではそのモジュールのメンバーを補完します。 |
| ファイルの構成をつかむ | VS Code のアウトラインでモジュールを展開し、その中の変数や `DEFINE` へ移動できます。長いファイルをスクロールして宣言を探す必要はありません。 |
| 書き間違いを見つける | 文法の誤り、存在しない名前、代入の型の不一致、真偽値にならない `case` の条件などを編集中に指摘します。大きなファイルでは意味チェックを省く設定もあります。 |
| モデルと検査を分ける | `#include "door.smv"` のように引用符で指定したローカルファイルからモジュールを読み込みます。入れ子の include もたどり、重複、循環、ファイルが見つからない場合は該当箇所に診断を出します。 |
| 検査式からモデルを読む | 名前にカーソルを置いて定義へ移動できます。ホバーや補完候補では宣言の内容を読めるので、たとえば `is_open` がどの条件を表す `DEFINE` か、検査式から離れずに確かめられます。 |
| モデルから検査式を探す | 名前を右クリックし、**NuSMV: Find Specifications Using Symbol** で、その定義を直接使う検査式を探せます。たとえば `is_open` の条件を変える前に、`front.is_open` を使う検査式を開いて意図を読み返せます。1件ならその場へ移動し、複数なら検査名やファイル名から選べます。 |
| 書いた性質を検査する | `NuSMV: Run Current Model` で外部の NuSMV を起動し、出力と真偽の件数を確認できます。実行の中断、ターミナルでの実行、対話シェルの起動もできます。 |

検査式の検索対象は、ワークスペース内のローカルな `.smv` ファイルと、開いているローカルの NuSMV ファイルです。同じ名前の別の宣言や、別の `DEFINE` を介した間接参照は数えません。

色分け・診断・補完・定義ジャンプと実行コマンドは元の拡張から引き継ぎました。LiCRuM 版では、これらをファイル分割に対応させ、定義のプレビューと検査式の逆引きを加えています。include で扱うのはモジュール全体です。編集中に外部のプリプロセッサを実行したり、マクロを展開したりはしません。モデルの分割例と実行の設定は[拡張の使い方](../langium-nusmv/README.md)を参照してください。

## 次に作る候補

以下は未実装の提案です。優先したいのは、入力を短くすることよりも、意図と違う検査式を書いたまま先に進むのを減らすことです。

1. **検査したいことから式のひな形を選ぶ。** 「開く経路が一つでもある」なら `CTLSPEC EF front.is_open`、「どの経路でもいずれ開く」なら `CTLSPEC AF front.is_open` です。どちらも正しく書けるので、文法エラーでは取り違えに気づけません。補完一覧にこの違いを示し、選んだひな形の条件部分にカーソルを置きます。参考になるのは、[TLA+ の VS Code 拡張](https://github.com/tlaplus/vscode-tlaplus#features)が構文のひな形を候補から挿入する仕組みです。NuSMV では [CTL 演算子の意味](https://nusmv.fbk.eu/tutorial/v27/tutorial.pdf)まで選ぶ前に読めるところに価値があります。
2. **モジュールの引数に名前を表示する。** `MODULE door(request, reset)` を使うとき、`door(button, ▏)` の位置で、今から渡すのは `reset` だと分かるようにします。[TypeScript の引数ヒント](https://code.visualstudio.com/docs/typescript/typescript-editing#_signature-help)をモデルの宣言に応用する案です。別ファイルの宣言でも順番を確認でき、引数の数が合わない場合は必要数を示せます。宣言に書かれていない型を決めつける必要はありません。
3. **未知の名前を、その場で正しい候補に直す。** `front.is_opne` の診断から、その `front` に実在する `is_open` を選べるようにします。[Go の言語サーバー gopls](https://go.dev/gopls/features/transformation)は診断に対応した修正を提示します。こちらでも候補は実際にその場所から参照できる名前に絞り、どの候補を採用するかは書き手が決めます。
4. **モデルをまたいで安全に名前を変える。** 0.11.1 では、別ファイルに `machine.completed` があっても、標準の参照検索・名前変更が `DEFINE completed` の宣言しか拾わない例がありました。今回の検査式の逆引きは、名前を一括変更する機能ではありません。改名するなら [gopls の参照検索](https://go.dev/gopls/features/navigation)と[名前変更](https://go.dev/gopls/features/transformation)のように、文字列ではなく宣言を基準に対象を選びます。検査式に加え、代入、条件、他の `DEFINE` でも参照を列挙し、新しい名前が既存の宣言と衝突しないことを確かめられる段階で取り組むのがよいです。
